# 관리자 담당자 서버 검색·페이지 처리 검증

2026-10-15 한국 시간. main `4babb00`에 기존 초안 PR #114를 병합해 갱신했다. 원래 커밋을 보존하며 신규 초대 검증·기존 담당자 재생성·초대 결과 불확실 잠금과 함께 검증했다.

## 화면과 조회 계약

관리자 조직 화면의 담당자 명단은 이름·발전소·활성 상태로 서버에서 검색하고 20명씩 조회한다. 이름과 ID로 정렬해 같은 이름의 순서도 고정한다. `%`, `_`, 역슬래시는 LIKE 검색에서 이스케이프하고 `*`는 입력 단계에서 거부한다.

전체 활성 담당자 수는 exact HEAD, 사업소별 활성 수는 `profiles(count)`로 조회한다. 검색 결과·페이지 번호와 독립된 집계이므로 검색 후에도 전체 수가 줄어들지 않는다. 사업소 목록과 수락 대기 초대의 서버 페이지 처리는 이번 범위에 포함하지 않는다.

검색·페이지 변경 시 기존 재생성 확인을 해제한다. 발급 직전에 선택 profile ID·이름·닉네임·소속·활성 상태를 현재 DB와 다시 대조한다. 변경·실패·지연이면 초대 발급을 시작하지 않는다. 읽기 성공만으로 기존 쓰기 작업의 불확실 잠금을 해제하지 않는다.

조직 집계·명단·재생성 직전의 읽기는 15초 제한을 두며, 화면 이탈과 대체 검색은 취소한다. 지연 후 수동 재시도를 제공하고 늦은 응답이 새 검색을 덮어쓰지 않게 한다. 신규 초대·재생성 자체의 쓰기 요청에는 읽기 제한이나 자동 재시도를 적용하지 않는다.

## 검증 중 보완

- 원래 `AdminManagerRoster.tsx`와 `adminManagerRoster.ts`는 Mac의 파일명 비교·모듈 해석에서 충돌했다. 조회 helper를 `managerRosterQueries.ts`로 분리했다.
- 원래 브라우저 모의 응답은 `Content-Range`를 CORS expose 헤더에 포함하지 않아 정확한 집계 수를 읽지 못했다. 실제 PostgREST와 동일하게 헤더를 노출했다.
- 사용되지 않는 폼 CSS 클래스 때문에 검색 입력이 기본 인라인 형태로 보이던 문제를 기존 관리자 입력 레이아웃으로 맞췄다.
- 기존 PR #87의 공백 이름·100자 제한·비활성 사업소 차단·계정 재생성 검사를 유지했다.
- 10월 13일 감사의 과거 수치·다음 순서는 다시 쓰지 않았다. 현재 기능 상태는 이 문서와 PR #114 결과를 따른다.

## 실제 로컬 DB 읽기 검증

```bash
pnpm check:admin-manager-roster-local
```

기존 HERO API `http://127.0.0.1:55321`·DB `127.0.0.1:55322`만 허용한다. 기존 활성 관리자 profile이 필요하며 없으면 중단한다. 로컬 CLI에서 키를 메모리로 읽고 짧은 로컬 시험 JWT로 관리자 RLS를 통과하는 GET·HEAD만 실행한다. 키·토큰·이름·ID를 출력하거나 파일에 저장하지 않는다. 계정·초대 생성·수정·삭제·DB 초기화는 하지 않는다.

확인 당시 활성 담당자 3명, 사업소 1개, 첫 페이지 3행·전체 3명이 일치했다. 사업소별 embedded count와 별도 HEAD count를 대조하고 활성·비활성 필터 2건을 확인했다. 실제 운영 DB나 실제 참여자 기록 검증으로 승계하지 않는다. 20행 초과 페이지·이름 필터와 실패 복구는 단위 및 모의 브라우저 검사에서 확인한다.

## 자동·브라우저 검증

- 모의 브라우저 360×800·390×844 총 28건 통과: 기존 초대·재생성 12건과 검색·페이지·전역 집계, 실패·지연·늦은 응답 배제, 재생성 전 ID 재확인, 읽기 재시도가 불확실 잠금을 해제하지 않는 경우.
- 조회 계약·기존 읽기 도우미 단위 17건 통과. 이름·발전소·상태의 서버 조건, 안정된 정렬, 잘못되거나 잘린 결과·누락 count의 거부, 페이지 끝 삭제 후 보정 등을 포함한다.
- 접근성 axe 위반 0, 검색 영역의 두 모바일 폭 가로 넘침 없음. 캡처 직접 확인.
- lint·TypeScript·프로덕션 빌드·초기 JS 예산·경로 분리·클라이언트 비밀정보·콘텐츠 승인 해시 검사 통과.
- 초기 필수 JS 514,886 B / gzip 149,352 B로 기존 상한 이내. Vite의 기존 500kB chunk 권고 경고는 남아 있다.

최종 CI·병합·운영 배포 여부와 실제 운영 파일 대조 결과는 [PR #114](https://github.com/worldinyj/HERO/pull/114)에 기록한다. 이 문서의 로컬 검사 통과만으로 운영 배포나 실기기·정식 출시 승인을 판정하지 않는다.
