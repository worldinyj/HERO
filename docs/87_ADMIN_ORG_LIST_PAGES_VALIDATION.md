# 관리자 사업소·수락 대기 초대 목록 페이지 검증

2026-10-16. 담당자 서버 검색 PR #114 다음 작업. 사업소와 수락 대기 담당자 초대를 화면에서 각각 20건씩 표시한다. 전체 건수와 현재 페이지를 별도로 안내하고 빈 목록·페이지 양끝 버튼을 제공한다.

## 조회와 안전장치

사업소 전체 목록은 코드 중복 검사·초대 대상 선택·담당자 소속 확인에 쓰인다. 초대 전체 목록은 발전소 운영 중지 영향 집계와 불확실한 발급·취소·재발급 결과의 수동 대조에 쓰인다. 화면 페이지와 이 전체 데이터는 분리했다. 페이지 밖 사업소가 선택지에서 사라지거나 페이지 밖 초대의 잠금이 해제되지 않는다.

전체 목록을 한 번의 무제한 요청에 의존하지 않고 서버에서 최대 200행씩 끝까지 읽는다. 각 구간의 exact count·예상 행 수·ID 중복을 검사하고, 이름 또는 생성 시각 뒤에 ID 정렬을 추가한다. 구간 실패·건수 변화·잘린 응답이면 전체 조회를 실패 처리하고 부분 결과로 기존 전체 목록을 교체하지 않는다. 재조회가 시작되면 이전 수동 대조 완료 상태를 무효화한다. 공유 15초 제한은 전체 조회에 적용되며, 중단된 조회는 후속 구간을 요청하지 않는다. 쓰기 자동 재시도는 추가하지 않았다.

모든 구간을 읽은 뒤 활성 사업소의 현재 invitation_epoch와 일치하는 초대만 화면과 집계에 반영한다. 검색 결과나 현재 20행을 대조 근거로 쓰지 않는다. 기존의 전체 재조회 후 명시적 확인, 일회용 링크 보관, 알 수 없는 발급 결과 잠금을 유지한다. 전체 조회 성공 자체로 잠금을 풀지 않는다.

이 변경은 **전체 대조용 구간 조회와 화면 페이지 처리**다. 방문한 페이지만 읽는 서버 검색은 담당자 목록에만 적용되어 있다. 사업소·초대는 여전히 전체 크기에 비례한 읽기·메모리가 필요하다. 여러 HTTP 구간은 DB 트랜잭션 스냅샷이 아니므로 동일 건수로 동시에 교체되는 모든 변경을 검출한다고 보장하지 않는다. 장기적으로 별도 읽기 전용 서버 계약을 도입하려면 현재 유효 초대 조건·전체 집계·알려진 작업 ID 및 ID를 받지 못한 생성 의도의 대조를 함께 설계해야 한다.

## 검증

- 구간 조회 단위 11건: 401행 범위, 빈 목록, 누락 count·잘린 응답·잘못된 ID·중복 ID·구간별 건수 변경·후속 구간 실패·중단 후 후속 요청 방지. 기존 조직 응답 검사와 합계 20건.
- 모바일 360×800·390×844 모의 브라우저 36건: 기존 담당자 초대·검색 회귀와 신규 사업소 201행·초대 203행(현재 유효 201행) 확인. 페이지 밖 선택지·전체 수·epoch 필터·일회용 URL 보존·페이지 밖 불확실 작업의 잠금과 명시적 전체 재확인을 검증한다.
- 접근성 axe 위반 0, 두 모바일 폭 가로 넘침 없음. 로컬 화면 캡처 확인.
- 기존 로컬 Supabase의 관리자 RLS에서 GET·HEAD로 사업소 1행·대기 초대 0행의 구간 조회와 전체 건수 대조 통과. 데이터 쓰기·초기화 0회. 대량 페이지는 모의 브라우저와 단위 검사 근거이며 실제 운영 데이터로 승계하지 않는다.

최종 head의 필수 CI·병합·배포 결과는 후속 PR에 기록한다. 실제 참여자 경쟁판 완료·서버 검증·내 기록 반영 결과와 두 체험자 상세 의견은 추가 접수되지 않았다. 정식 출시의 실기기·오디오·사내망·법무/개인정보·30명 파일럿·별도 staging/동일 SHA RC 승인 근거는 계속 대기다.
