# 관리자 감사 이력 조회

## 사용 방법

활성 관리자 계정으로 `/admin/audit`에 접속하거나 조직·시나리오 관리 화면의 **감사 이력** 링크를 선택한다.

- 전체 이벤트 또는 이벤트 종류를 선택하고 시작일·종료일을 입력한 뒤 **조회**한다.
- 날짜와 시각은 한국 시간(Asia/Seoul) 기준이며 종료일 하루 전체를 포함한다.
- 한 페이지는 50건이며 등록 ID 내림차순이다. **다음 페이지**는 마지막 표시 ID보다 작은 기록을 조회한다. 조회 중 새 기록이 추가되어도 offset 이동으로 같은 기록이 중복 표시되지 않는다.
- **최신 기록 새로고침**은 적용 중인 조건을 유지하고 첫 페이지로 돌아간다. **필터 초기화**는 전체 이력을 다시 조회한다.
- **기록 식별 정보**에서 이벤트 코드, 처리자·조직·대상의 ID를 대조한다. 알려지지 않은 이벤트도 원래 코드로 표시한다.

## 데이터와 권한

기존 `audit_logs` 테이블의 `id, actor_user_id, plant_id, action, entity_type, entity_id, created_at`만 읽는다. `metadata`, 실명·닉네임, 초대 토큰·링크는 이 화면에서 조회하지 않는다. 변경 전후의 상세 payload 조회와 CSV 내보내기는 이번 범위에 포함하지 않는다.

기존 DB RLS의 `audit_logs_admin_select` 정책과 활성 관리자 화면 게이트를 사용한다. Player·Plant Manager는 DB에서 감사 이력을 읽을 수 없으며 화면도 캠페인으로 이동한다. DB 마이그레이션·Edge Function 변경·운영 데이터 수정은 필요 없다. 로그 수정·삭제 기능은 없다.

통신·권한 오류나 잘못된 응답은 조회 실패로 표시하며, 빈 이력으로 처리하지 않는다. 필터·페이지 변경 후 이전 결과는 제거하고 최신 요청만 반영한다.

## 검증

- `auditHistory.test.ts`: 한국 날짜 경계, 잘못된 기간, 잘못된 ID·정렬·중복 응답 거절, metadata 제외.
- `e2e/admin-audit-history.spec.ts`: 두 모바일 크기의 커서 페이지 이동, 기간·이벤트 필터, 빈 결과, 오류·재시도, 접근 제한, 가로 넘침·axe 접근성. 로컬 API 모의 응답을 사용하며 실제 운영 로그를 생성하지 않는다.
- DB 권한·불변성 검증은 기존 `supabase/tests/rls_role_matrix.test.sql`에서 수행한다.

실제 운영 관리자로 로그인한 조회 결과와 모바일 실기기 사용성은 별도 확인 대상이다.
